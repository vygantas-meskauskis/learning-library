Becoming an AI-Native Designer

A practical guide for mid-to-senior UX/UI designers (October 2026)

Who this is for: a designer who already knows UX/UI and Figma well and wants to work the way the best AI-native designers work today. You'll learn to build design systems that both people and AI can use, connect Figma to code without writing any code yourself, and use AI every day without lowering your standards.

What "AI-native" means here

An AI-native designer isn't someone who uses ChatGPT a lot. It's someone whose work is set up so AI can amplify it:

  • Their design system is structured so that AI tools build with it rather than around it.
  • Their knowledge (users, rules, standards) is written down where AI tools can read it.
  • They delegate drafts, variations, busywork and code to AI, and keep judgment, taste and decisions for themselves.
  • They know where everything lives and who (or what) does what: Figma, the AI tools, the developers' code, and the files that connect them.

This guide teaches that setup and those habits.

How the guide works

One story runs through every chapter. You join Movewell, a startup with a mobile app (iOS and Android) for booking local fitness and wellness classes such as yoga, pilates, spin, climbing intros and sound baths. You're the new senior product designer. Along the way you will:

  1. Imagine the ideal setup if we started today (greenfield).
  2. Face reality: an inherited, messy Figma file and an app that drifted from it.
  3. Rebuild the design system so that people and AI can use it.
  4. Connect Figma to the developers' code, and let an AI agent build screens from your designs.
  5. Use the system every day with AI: designing, prototyping, research.
  6. Design the app's first AI feature.
  7. Learn how to work with developers and PMs in this new setup.

Chapter 1: Orientation, the AI-native designer's map

⏱ About 25 min · You'll learn: what changes in a senior designer's work, where everything lives, and who (or what) does what.

📖 Story: your first day at Movewell

Movewell has about 25 people. The app lets people find and book local fitness and wellness classes, from yoga and pilates to spin, climbing intros and sound baths. It's been live for two years on iOS and Android.

You meet the people you'll work with most:

Person Role What they care about
Maya Product manager Bookings per user, retention, shipping on time
Jonas Tech lead Code quality, not rebuilding things twice
Ana Mobile developer Clear specs, fewer "is this the right blue?" questions
Leo Front-end developer who maintains the shared components Consistency between Figma and code
Priya Researcher (contract, 2 days/week) Real user evidence
Sam Junior designer Learning, speed

On day one, Maya shows you a screen she "designed" in ChatGPT for a new feature. Ana mentions that the developers' coding agent has been "guessing the styling" because the Figma file is "a bit of a mess". Leo says: "Figma and the app haven't matched for a year."

This is the reality the guide works with: everyone is already making UI with AI, and nothing connects their efforts.

Your job as a senior AI-native designer is to make sure everything they generate, whether a PM's mockup, a developer's agent output or Sam's explorations, comes out on-system, on-brand and grounded in what users need.

🧠 Concept 1: What actually changes for a senior designer

Before AI AI-native
You make most screens yourself You direct and judge: AI drafts, you decide
The design system is a Figma library for designers The design system is the source of truth for people and AI
Standards live in your head, in Slack and in decks Standards are written down where AI tools read them
Handoff = specs and redlines Handoff = structured design + context, which agents read directly
You check the built app at the end You review running UI early and often, including AI-built UI
Prototypes are clickable pictures Prototypes can be working apps with real data

What does not change: talking to real users, judgment, taste, accessibility, clarity, and owning the quality of what ships.

💡 The key mental shift: you're no longer only designing screens. You're also designing the inputs that AI uses to make screens: the system, the rules and the context.

🧠 Concept 4: Three kinds of "AI" you'll use

People say "AI" for very different things. Keep them apart:

Kind Example Good for Not good for
Chat assistant ChatGPT (Chat) Thinking, writing, research, critique, planning Anything that needs your actual files unless you attach them
AI inside a tool Figma agent, Figma Make Working on your designs with your library Work outside that tool
Agent Codex; ChatGPT Work Multi-step tasks: read Figma, write code, run it, fix errors Decisions about what's right for users

An agent is an AI that can take a goal, plan steps, use tools (read a file, run code, open Figma) and check its own results. That's what makes "design to code without coding" possible.

🧾 Real artifact: Maya's ChatGPT mockup, and what was wrong with it

Maya asked ChatGPT: "Design a screen for booking a recurring weekly yoga class." The result looked fine, but:

  • It used a purple primary button. Movewell's brand colour is teal.
  • It said "Reserve". Movewell uses "Book" everywhere.
  • It put the cancellation policy in small grey text under the button. Research showed users complain about surprise cancellation fees.
  • It invented a new date-picker style that doesn't exist in the app.

None of this is Maya's fault, or ChatGPT's. The AI had no context. It produced the average booking screen. By the end of this guide, the same prompt from Maya will produce something on-brand and grounded in research, because the context will be there.

Chapter 2: AI essentials for designers

⏱ About 30 min · You'll learn: the 20% of AI knowledge that explains 80% of what happens, how to set up ChatGPT as a product-aware partner, and how to prompt, critique and verify like a senior designer.

📖 Story: the "average" problem

In your first week you ask ChatGPT to help with the class-details screen. It suggests a hero image, a big "Book now" button, a rating row, an instructor bio and a map. It's perfectly reasonable, and exactly what every booking app has.

Priya, the researcher, reads it and says: "Our users care most about two things this doesn't mention: whether the class is beginner-friendly, and what happens if they cancel. That's in every interview."

ChatGPT didn't know that. Nothing in the chat told it. This chapter explains why that happens and how to fix it permanently.

🧠 Concept 1: How AI models work (the useful version)

The AI behind ChatGPT, the Figma agent and Codex is a large language model (LLM). It's trained on huge amounts of text, code and images to predict plausible next content. Four consequences matter for designers:

mindmap
  root((How AI behaves))
    It predicts the plausible
      Usually right
      Sometimes confidently wrong
      Verify facts and numbers
    It drifts to the average
      Typical app patterns
      Generic copy
      Context pulls it to YOUR product
    It only knows what it sees
      No memory of your product by default
      Projects, files, context give it memory
    It varies every run
      Great for exploring
      Bad for consistency
      Systems and rules create consistency
Behaviour What it means for you
Plausible, not true It can invent statistics, quotes and "best practices". Verify anything you'll rely on.
Pulls to the average Without context you get the most common pattern. Context is how you get your product.
Only knows what it sees It has no idea about Movewell's users, brand or decisions unless they're in the chat, a file or a project.
Different every time Running a prompt again gives new ideas (good for exploring). Two people get two different designs (bad for consistency), so consistency comes from your system and rules, not from prompts.

Five failure modes to recognise instantly

  1. Hallucination: confident but false facts, sources or numbers.
  2. Sycophancy: it agrees with you and praises your work. Ask for critique, not opinions.
  3. Averageness: generic patterns and copy. Add context.
  4. Narrowness: ask for 10 ideas and get 10 variations of one idea. Force different strategies.
  5. Drift: in long chats it forgets earlier constraints. Restate them, or start fresh with a summary.

🧠 Concept 2: Context is the whole game

Context is everything the AI can see when it works: your message, attached files, project instructions, connected tools, the Figma library, and so on.

The best AI-native designers spend more effort on context than on prompts. Their prompts are often short and casual, because the context does the heavy lifting. NN/G's 2026 research with AI power users found exactly this: they invest in context libraries and dictate short prompts (NN/G).

NN/G describes three kinds of context (source):

Kind Meaning Movewell example Where it lives
Global Rarely changes; applies to everything Brand, design principles, users, glossary ChatGPT Project instructions, DESIGN.md, UX.md, Figma library
Local Specific to one task The brief for "recurring bookings", the Figma frame Attached files, links, the current chat
Ambient Raw streams the AI can sift through Slack threads, meeting notes Connected apps (use carefully)

💡 Rule of thumb: write global context once, attach local context per task, and be careful with ambient context.

🧾 Real artifact: Movewell project instructions (excerpt)

You are a senior product design partner for Movewell, a mobile app (iOS + Android)
for discovering and booking local fitness and wellness classes.

USERS (from research, 2026):
- Primary: busy professionals 25–45 who book 1–3 classes/week, often on their commute.
  They want to book in under 30 seconds and hate surprise fees.
- Secondary: beginners trying a new activity. Their #1 worry is "will I fit in /
  is this too hard?" → beginner-friendliness must be visible.
- Studios set cancellation rules; users must see them BEFORE booking.

VOICE: warm, clear, encouraging, never pushy. Sentence case. No exclamation marks
in errors. Use our words: "book" (not reserve), "class" (not session), "studio"
(not gym), "credits" (not points).

DESIGN: we have a design system (see DESIGN.md). Always suggest existing
components first and say when something new would be needed.

HOW TO WORK WITH ME:
- Be direct. Critique honestly; no flattery.
- When unsure, say so and tell me what to verify.
- When giving options, make them genuinely different and recommend one.
- Cite sources for factual claims; flag anything uncertain.

Add files to the project: UX.md, DESIGN.md (both covered in Chapter 8), the glossary, and research summaries.

⚠️ Data rule: don't put personal user data, unreleased financials or passwords into AI tools your company hasn't approved. Summarise and anonymise.

🧠 Concept 4: Prompting like a senior

Prompts matter less than context, but a clear prompt still helps. A reliable structure:

Part Example
Goal "Write empty-state copy for 'My bookings'."
Context (only what isn't already in the project) "Shown to new users who haven't booked yet; most arrive from onboarding."
Constraints "Headline ≤ 6 words, body ≤ 20 words, one action."
Output format "Table with 6 options: headline, body, button, rationale."
Quality bar "Make the options genuinely different. Recommend one and say why."

Diverge → converge

AI is great at diverging (many options) if you push against its pull to the average. You converge (choose, combine, justify).

Give me 6 concepts for the class-details screen, each built on a DIFFERENT idea:
1) "decide in 5 seconds" (scannable facts first)
2) "reassure beginners" (difficulty + what to expect)
3) "social proof" (who goes, reviews)
4) "instructor-led" (the person matters most)
5) "logistics first" (when, where, what to bring, cancellation)
6) borrow from a non-fitness domain (airline, restaurant, cinema)
For each: one-line concept, who it's best for, biggest risk.

Critique without flattery

Never ask "what do you think?". Ask for a structured review:

You are a strict senior UX reviewer. Review the attached class-details screen for
a beginner deciding whether to book. List the 7 most serious issues, ranked by
severity (critical/major/minor), each with: the usability heuristic it violates,
where it is, why it matters for this user, and a concrete fix. No praise.
Say when you're unsure.

Verify in proportion to risk

Risk Example What to check
Low Brainstorms, first drafts Does it make sense?
Medium Research summaries, competitor scans Check the 3 claims you rely on most against sources
High Shipped copy, accessibility claims, anything legal or financial Full human review, use a real tool (for example a contrast checker), get sign-off

🧠 Concept 5: AI inside Figma, a first look

🔧 The Figma agent works on your canvas: select layers and press Cmd/Ctrl + Enter, or open the Agents sidebar. It can generate and remix designs, do busywork and give feedback. You can also create custom skills: reusable instructions you trigger with a slash command such as /design-crit or /follow-ds-guidelines. They follow the open Agent Skills format and work in Figma Design and Figma Make (Figma Help). Skills are how your best prompts become permanent tools. Chapter 10 builds several.

🧠 Concept 1: The principle, "one decision, one place, flows everywhere"

In an AI-native setup, every design decision is made once, stored in one place, and flows automatically to everything that needs it: Figma screens, the app, prototypes, and every AI tool.

Example: Movewell decides its primary action colour is a slightly darker teal for better contrast.

flowchart LR
  D["Decision:<br/>action colour = teal 700"] --> V["Figma variable<br/>color/action/primary"]
  V --> S["All Figma screens<br/>update instantly"]
  V --> T["Tokens in code<br/>(synced, not retyped)"]
  T --> A["The app<br/>iOS + Android"]
  V --> M["Figma Make prototypes<br/>(via Make kit)"]
  V --> X["DESIGN.md<br/>(generated / updated)"]
  X --> AI["ChatGPT · Codex · any agent"]

Anti-pattern: the same colour typed as a hex code in 40 Figma layers, 25 code files and a brand PDF. Then every change becomes a hunt, and AI tools pick whichever value they see first.

🧠 Concept 3: Name things once, together

The single most valuable greenfield decision: designers and developers agree on names before anything is built, and use them everywhere.

🧾 Real artifact: Movewell's naming agreement (excerpt)

Concept Figma Code (what developers see) Notes
Primary action colour color/action/primary color.action.primary Same words, different separator
Card background color/bg/surface-raised color.bg.surfaceRaised Developers' naming style for multi-word names
Medium spacing space/md space.md
Button Component Button Component Button

You don't need to understand code to create this table. You need one meeting with a developer and the habit of never renaming things alone.

Why it matters for AI: when an agent reads your Figma file through the MCP server and sees Button / variant=primary, and the code also has Button with variant="primary", it connects them correctly. When Figma says "CTA big teal" and the code says PrimaryButton, it guesses, and guesses wrong.

Chapter 5: Tokens and variables, done right

⏱ About 35 min · You'll learn: what tokens are, the primitive → semantic structure, naming that people and AI understand, modes (light/dark), how Figma variables implement all this, and how AI helps you build them.

📖 Story: from 14 teals to 3 roles

The audit showed 14 teals. Ask "what is each teal for?" and the answers collapse into three roles:

  1. The colour of actions (buttons, links, selected states)
  2. An accent for highlights (a "beginner-friendly" badge)
  3. A subtle background for selected cards and chips

Tokens are how you turn "14 colours" into "3 decisions", and how you make sure every person and every AI tool uses the right one.

🧠 Concept 1: What a token is

A design token is a named design decision stored as data:

color / action / primary  =  #0F7A6C

The name says what it's for. The value says what it is. Everyone (Figma, code, AI) uses the name, so when the value changes, everything updates.

In Figma, tokens are variables 🔧 (organised in collections, with modes).

Rule: components and screens use semantic tokens only. This lets you:

  • Theme: dark mode points semantic tokens at different primitives, and the components don't change.
  • Rebrand: change a primitive or an alias, and everything follows.
  • Help AI: color/text/danger tells the AI when to use it; red/600 doesn't.

💡 Start with two tiers. Add component tokens only when you genuinely need them (for example, a component that must differ from the general rule).

🧠 Concept 3: Naming that people and AI understand

Use the pattern category / property / role / state:

color/text/primary            color/bg/surface            color/border/default
color/text/secondary          color/bg/surface-raised     color/border/focus
color/text/on-action          color/bg/selected           color/action/primary
color/text/danger             color/feedback/danger-bg    color/action/primary-hover

space/xs (4) · space/sm (8) · space/md (16) · space/lg (24) · space/xl (32)
radius/sm (6) · radius/md (12) · radius/lg (20) · radius/full

Good names are:

  • Purposeful: they describe intent (action/primary), not appearance (teal-button).
  • Predictable: someone can guess a name they've never seen.
  • Shared: identical words in Figma and code (Chapter 3's naming agreement).

🧠 Concept 4: Modes

A mode is an alternative set of values for the same variables. In Figma, a collection can have several modes 🔧.

  S["color/bg/surface"] -- "Light mode" --> L["neutral/0 #FFFFFF"]
  S -- "Dark mode" --> D["neutral/950 #121517"]
  T["color/text/primary"] -- "Light mode" --> L2["neutral/900"]
  T -- "Dark mode" --> D2["neutral/50"]

Common mode types:

Mode set Use
Light / Dark Theme
Comfortable / Compact Density (spacing variables)
Brand A / Brand B White-label products
iOS / Android Platform-specific differences, only where real ones exist

Switch a frame's mode in Figma and all bound values change. If a frame breaks in dark mode, something isn't using a semantic variable. That makes dark mode a free health check.

🧠 Concept 5: Scoping and descriptions

  • Scoping 🔧 limits where a variable appears. For example, text colours appear only in text-fill pickers, and spacing only in gap and padding fields. Fewer wrong choices for people and for the Figma agent.
  • Descriptions: every semantic variable gets one line on when to use it and when not to:
color/text/secondary — Supporting text: metadata, helper text, timestamps.
Not for disabled text (use color/text/disabled). Contrast ≥ 4.5:1 on bg/surface.

These descriptions travel to developers and AI tools. They're one of the cheapest, highest-impact things you can write.

🧠 Concept 6: Typography, spacing, radius, elevation

Category Recommendation
Typography Text styles with role names: heading/lg, heading/md, body/md, body/sm, label/md, caption. 6–8 is usually enough. Bind sizes and line heights to number variables if your setup supports it.
Spacing A 4px-based scale with semantic names (xs–xl). Bind auto-layout gaps and padding to variables.
Radius 3–4 values plus full.
Elevation 2–3 shadow styles max (shadow/sm, shadow/md). Keep dark mode in mind.
Motion Durations and easings as variables or a documented table, such as motion/fast = 120ms.

🧠 Concept 7: The standard behind it (DTCG)

It's a shared format so tokens can move between tools (Figma, code tools, documentation) without retyping. Figma, Penpot, Sketch, Framer, Style Dictionary, Tokens Studio, Supernova, zeroheight and others are listed as adopters or participants (designtokens.org).

You don't need to read the spec. Just know that a standard exists, so your variables can be exported and synced to code reliably (Chapter 7).

Chapter 6: Components that people and machines understand

⏱ About 35 min · You'll learn: how to build components with clean properties, all states, accessibility and descriptions, so that designers, developers and AI tools all use them correctly. Plus how AI speeds up the boring parts.

📖 Story: one ClassCard to rule them all

Movewell had five versions of the "class card" (the card showing a class in search results). Each designer made their own. The coding agent built a sixth.

You'll replace them with one ClassCard component: well-structured, documented and connected to code. Here's how to make it something AI can't misuse.

🧠 Concept 1: What an agent "sees" in your component

When an AI tool (the Figma agent, Figma Make, or a coding agent through the MCP server) looks at a component instance, it reads structure, not pixels:

      ClassCard

    Variables bound

    Layer names

    Description
      when to use · when not
      accessibility · code name
    Code Connect

If these are clean, AI uses your component correctly. If they're messy, AI guesses.

🧠 Concept 2: Properties, the component's "controls"

🔧 Figma components have properties:

Property type Use for ClassCard example
Variant Real structural or visual differences layout = list / compact / featured
Boolean Show/hide a part showBeginnerBadge, showPrice
Text Editable text content title, studioName
Instance swap Swap a nested component leadingImage (photo / instructor avatar)

Avoid "variant explosion." If you multiply layout × size × state × badge × image, you get hundreds of variants. Use booleans and instance swaps for optional parts, and keep variants for real differences.

Name properties like the code props. If developers' code has layout="compact", your Figma property is layout = compact, not "Type = Small card". (Chapter 3's naming agreement.)

🧠 Concept 3: States: the part AI most often forgets

Every interactive component needs its states designed. AI-generated UI notoriously skips them.

Component States to design
Button default, hover/pressed, focus, disabled, loading
Input empty, filled, focus, error (+ message), disabled, read-only
ClassCard default, pressed, full (waitlist), booked, cancelled, loading skeleton
Lists and screens empty, loading, partial, error, offline, very long content

Make states variants (state = default / booked / full / loading) or documented patterns, so they exist in the system and AI can find them.

🧠 Concept 4: Structure: auto layout and layer names

  • Auto layout everywhere, with gaps and padding bound to spacing variables.
  • Content-driven sizing (hug or fill), so long titles and translations don't break things.
  • Semantic layer names: title, meta, time, price, badge, cta. The Figma agent can rename layers for you.
  • No hidden junk: remove invisible layers and old leftovers.

🧠 Concept 5: Accessibility built into components

Bake accessibility into the component, and every screen (and every AI generation) inherits it:

  • Contrast: text ≥ 4.5:1; large text and essential UI parts ≥ 3:1 (WCAG 2.2 AA).
  • Visible focus using color/border/focus.
  • Touch targets: at least 44×44pt on iOS and 48×48dp on Android are common platform guidelines (WCAG 2.2's AA minimum is 24×24 CSS px).
  • Don't rely on colour alone: "Full" isn't just grey; it has a label.
  • Labels: inputs always have a visible label. Icon-only buttons have an accessible name in the description.
  • Text scaling: check the component with larger text (Dynamic Type / font scaling).

🧠 Concept 6: The description is a mini-spec for people and AI

🔧 Every component has a description field. AI-native designers treat it as a compact spec:

🧠 Concept 2: Which side is the source of truth?

🧠 Concept 2: DESIGN.md, visual rules for AI

DESIGN.md is an open format from Google Labs (April 2026, still a draft "alpha" spec) for describing a product's visual identity to AI coding tools (GitHub; NN/G coverage). It has two parts:

  1. Exact values (tokens) at the top, in a structured block: colours, typography, radius, spacing.
  2. Plain-language rules: what values are for, how to apply them, do's and don'ts.

"Tokens give agents exact values. Prose tells them why those values exist and how to apply them." (DESIGN.md README)

🧾 Real artifact: Movewell DESIGN.md (excerpt)

  text-primary: "#1D2125"

## Overview
Warm, energetic but calm. Feels like a friendly front desk, not a sales funnel.

## Colors
- action-primary is the ONLY colour for primary actions and links.
- accent-beginner is ONLY for the "Beginner-friendly" badge. Never decorative.
- danger only for errors/destructive actions, always with icon or text.

## Components
- Always use existing components (Button, ClassCard, TimeSlotChip, BookingSummary...).
- One primary button per screen section.

- Do: show cancellation rules before the Book button.
- Don't: use gradients, more than one shadow level, or emoji in UI text.

🧠 Concept 3: UX.md, users and behaviour rules for AI

DESIGN.md covers how it looks. UX.md covers who it's for and how it behaves. NN/G proposes UX.md as a companion to DESIGN.md, holding research insights, interaction standards, a glossary, user models and world models (NN/G).

The key technique: write research findings as constraints the AI can follow.

🧾 Real artifact: Movewell UX.md (excerpt)

## Users
- Busy professionals (25–45): book 1–3 classes/week, often on their commute,
  one-handed. Want to book in < 30 s. Hate surprise fees.
- Beginners: worry "is this too hard / will I fit in?"

## Insights → constraints
| Insight (evidence)                                        | Constraint for anything we generate              |
|-----------------------------------------------------------|--------------------------------------------------|
| Users feel tricked by late-cancel fees (14/18 interviews) | Show the cancellation rule BEFORE the Book button |
| Beginners skip classes that look intense (9/12)           | Show difficulty + "Beginner-friendly" when true   |
| Most bookings happen one-handed on the move (analytics)   | Primary actions in thumb zone; ≤ 3 taps to book   |

## Interaction standards
- Booking: confirm with a summary sheet, then success with "Add to calendar".
- Cancel: allowed with undo for 10 s if free; confirmation dialog if a fee applies.
- Errors: what happened + what to do next; never blame the user.

## Words (glossary)
book (not reserve) · class (not session) · studio (not gym) · credits (not points)

Full template: toolkit/UX.md.

🧠 Concept 4: AGENTS.md, rules for coding agents

AGENTS.md lives in the code and tells coding agents (Codex and others) how to behave in this project. Developers write the code rules. You co-write the design-system rules. Figma's own recommended rules are a good base (Figma docs).

🧾 Real artifact: the design section of Movewell's AGENTS.md

## Design system rules (owned by Design)
- IMPORTANT: Always use components from the app component library.
  Never create a new Button, Card, Chip, Sheet, etc. if one exists.
- IMPORTANT: If a needed component or state doesn't exist, STOP and list what's
  missing. Don't invent UI.
- Never hardcode colours, spacing, radius or font sizes. Use tokens.
- Read DESIGN.md and UX.md before any UI work.
- Use glossary words exactly (book, class, studio, credits).
- Accessibility: labels on inputs, visible focus, contrast ≥ 4.5:1,
  touch targets ≥ 44pt (iOS) / 48dp (Android).

## Figma MCP flow
1. Get design context for the exact Figma node linked.
2. Get a screenshot of it for visual reference.
3. Treat Figma MCP output as design intent; build with OUR components and tokens.
4. Compare against the screenshot before finishing.

That "stop and list what's missing" rule is one of the most valuable lines you can add. It turns agent guesswork into a visible list of design-system gaps.

Full template: toolkit/AGENTS.md.

🧠 Concept 5: Context in Figma itself (descriptions, skills, Make kit)

  • Make kit: in Figma Make, a kit can import variables and styles from your library, include code packages for components and tokens, and add guidelines on how to use them (Figma Help). Your DESIGN.md "Do / Don't" section makes good kit guidelines.

🧠 Concept 7: Keep context alive (and avoid a "big ball of mud")

NN/G found that even AI power users let context files go stale, rarely check what AI changed in them, and grow messy, fragile setups piece by piece, which NN/G calls a "big ball of mud" (context libraries; big ball of mud).

Simple habits:

  • Few files, clear names: DESIGN.md, UX.md, glossary, AGENTS.md (design section). Resist creating 20 files.
  • Update from failures: when AI gets something wrong, ask "which line of context would have prevented this?" and add it.
  • Let AI edit, then you review: "Update UX.md with today's research findings as constraints; show me the diff."
  • Date and source every research insight.
  • Remove stale rules. Old rules confuse AI as much as missing ones.
  • No personal data or secrets in any context file.

Your part as a designer

  2. Align properties with props before mapping (naming agreement, Chapter 3).

  4. Don't rename components or properties without telling developers. Mappings depend on the names.
  5. Track coverage: "12 of 30 components connected" is a great health metric.

Chapter 11: Prototyping with Figma Make and friends

⏱ About 35 min · You'll learn: when you need an interactive prototype, how to build one in Figma Make on top of your design system, how to give it realistic data, how to test it with real users, and how a prototype can feed production without becoming it.

📖 Story: does "repeat weekly" actually make sense?

Your recurring-bookings design looks clean in static frames. But the real questions are about behaviour: What happens when the studio cancels one week? Does the user understand they'll be charged weekly? Can they skip one week easily?

Static screens can't answer these. You need something people can use.

🧠 Concept 1: Static or interactive?

flowchart TB
  Q{"What are you trying to learn?"}
  Q -- "first impression, layout, visual hierarchy, copy comprehension" --> S["Static Figma frames<br/>(or simple click-through)"]
  Q -- "navigation / findability" --> CT["Click-through prototype"]
  Q -- "behaviour: filters, forms, rules,<br/>state over time, real data" --> I["Interactive prototype<br/>(Figma Make)"]
  Q -- "AI behaviour<br/>(different answers each time)" --> AI["Interactive, connected<br/>to a real model"]

Rule of thumb: build the lowest fidelity that answers the question. AI makes high fidelity cheap to create, but not free: it slows iteration and invites "can we ship this?".

Real-world evidence

NN/G's 2026 article on AI prototyping describes two real cases (NN/G):

  • Ramp: a designer used an AI coding tool (Cursor) to prototype a complex policy editor. Participants tested it with their own sanitised data, and the team found a usability problem they "couldn't have found… without an interactive prototype". Concept to demo took about three weeks.
  • Purdue University: a traffic-data filter interface rebuilt as an interactive prototype (with v0 and Bolt) got more specific feedback than static wireframes. Participants treated static screens as "too early" to critique in depth.

🧠 Concept 3: A reliable process for AI prototypes

Adapted from NN/G's six steps (source):

flowchart LR
  A["1 · Decide what<br/>must work"] --> B["2 · Make the<br/>design decisions"]
  B --> C["3 · Prepare<br/>realistic data"]
  C --> D["4 · Write a<br/>structured prompt"]
  D --> E["5 · Generate in Make<br/>(with kit + frames)"]
  E --> F["6 · Iterate,<br/>then pilot-test"]
  1. Decide what must work to answer your research questions, and what doesn't need to.
  2. Make the design decisions first. If you leave decisions to the AI, it fills gaps with average choices.
  3. Prepare realistic data: real exports (anonymised, if allowed) or synthetic data from ChatGPT.
  4. Write a structured prompt (markdown works well).
  5. Generate, attaching your frames and using your kit.
  6. Iterate one change at a time, then pilot-test with a colleague before real sessions.

🧠 Concept 5: The fidelity trap

A polished prototype prompts "looks great, can we just ship it?". NN/G warns that AI prototypes can look complete while containing wrong patterns, confusing hierarchy and repeated elements. A strong designer should review before anything goes toward production (NN/G). From the engineering side, a prototype also lacks real security, performance, error handling and tests.

How to handle it

  • Label links: "Prototype — for research".
  • Present what you learned, not the prototype itself.
  • Offer the path to production: validated design → built with system components (Chapter 12).

Chapter 13: Research in an AI-native workflow

⏱ About 25 min · You'll learn: where AI genuinely helps research and where it misleads, a safe synthesis workflow, why synthetic users aren't users, and how to turn findings into context that improves every AI output.

📖 Story: "Can't we just ask ChatGPT what users want?"

Maya, half-joking: "Could we skip interviews and ask ChatGPT to role-play our users?" Priya, not joking: "Then we'd be designing for the average user of every app ever, not ours."

Both have a point. AI makes research faster and cheaper, but it can't replace contact with real people.

🧠 Concept 1: Where AI helps, and where it doesn't

Research activity AI role Watch out for
Desk research, competitor scans ✅ Strong: use ChatGPT Work mode or search, and open the sources Invented or outdated facts; verify key claims
Interview guides, screeners, surveys ✅ Strong: drafting and reviewing for bias Leading questions it introduces itself
Transcription and note-taking ✅ Strong (approved tools, consent) Personal data handling
First-pass clustering of notes ⚠️ Helpful Wrong focus; invented or merged quotes; minority findings averaged away
Interpretation and insights ⚠️ Assistant only It sounds confident; you own the conclusions
Talking to and observing users ❌ Not replaceable —
Synthetic users ⚠️ For rehearsing and pilot-testing materials only Not evidence (see below)

This matches practice. NN/G's 2026 survey of 521 UX practitioners found AI is used most for desk work and least when real users are involved (NN/G).

🧠 Concept 2: Synthetic users are not users

NN/G compared 120 AI-generated respondents with 604 real humans on the same open question. Both datasets reached the same broad conclusion, but the synthetic answers had far less variety ("mode collapse"), and the platform sometimes reworded the question, a methodological risk (NN/G).

What that means for you:

  • ✅ Use synthetic users to rehearse an interview or pilot-test a survey's wording.
  • ✅ Use them to generate hypotheses you then test.
  • ❌ Don't use them as evidence for decisions.
  • ❌ Don't let them replace usability testing.

🧠 Concept 3: A safe synthesis workflow

flowchart LR
  R["1 · You skim the raw material<br/>(note your own impressions)"] --> C["2 · AI clusters<br/>WITH quotes + participant IDs"]
  C --> V["3 · You verify quotes,<br/>merge / split / rename themes"]
  V --> X["4 · AI: 'what contradicts each theme?<br/>who doesn't fit?'"]
  X --> W["5 · You write the insights<br/>(AI can polish wording)"]

The clustering prompt (anonymised notes only)

Here are anonymised notes from 8 interviews (P1–P8) about booking classes.
Cluster them into themes. For each theme: name, one-sentence insight, supporting
quotes WITH participant ID and line reference, number of participants.
Then list: evidence that contradicts each theme, and participants who don't fit
any theme. Do not invent or merge quotes.

The verification habit

  • Pick the 3 themes your decisions depend on most and check every quote against the source.
  • If any quote is invented or misattributed, redo the synthesis. Don't patch it.

Chapter 14: Designing the AI feature, "Find me a class"

⏱ About 35 min · You'll learn: how to decide whether a feature should use AI, how to design for unpredictable output, trust and control, how to write an AI behaviour spec and a test set, and how to add AI patterns to your design system.

📖 Story: the CEO wants "AI search"

The CEO saw competitors adding chatbots and asks for "AI in the app". Maya proposes a chat assistant. You suggest starting from the user problem instead.

Research (Chapter 13) showed users often know roughly what they want ("something relaxing after work, not too far, this week") but struggle with filters. That's a real problem AI can help with: turning a vague wish into a good shortlist.

The feature becomes "Find me a class": type or say what you want, and get matching classes you can book.

🧠 Concept 1: Value first, AI second

NN/G is blunt: "Powered by AI" is not a value proposition, and AI features must solve real user problems (study guide). NN/G's four AI "superpowers" are content creation, summarisation, basic data analysis and perspective-taking (source).

Value-first test for "Find me a class":

Question Answer
Real user problem? ✅ Users struggle to translate vague wishes into filters (research)
Better than non-AI? ✅ Filters exist but are underused; the natural language input fills the gap
Uses an AI superpower? ✅ Interpreting intent + summarising options ("perspective-taking", basic analysis)
Cost of a wrong answer? 🟡 Low if users see and correct the interpretation; high if the AI books on its own
Narrow scope? ✅ Only finds classes; doesn't do everything

Narrowly scoped AI features are easier to understand and adopted more (NN/G).

🧠 Concept 2: Not a chatbot: a hybrid interface

NN/G warns that AI chat is not always the answer (source). Users struggle to express what they want in words (the articulation barrier), and hybrid interfaces that combine a text prompt with regular UI controls help (source).

flowchart LR
  I["User types / says:<br/>'something relaxing after work,<br/>near me, this week'"] --> P["AI interprets intent"]
  P --> C["Shows interpretation as<br/>EDITABLE CHIPS:<br/>Yoga · Pilates · Sound bath<br/>Tue–Thu after 18:00 · ≤ 3 km · Beginner-OK"]
  C --> R["Results as normal<br/>ClassCards + 'why this' line"]
  C -- "user edits a chip" --> R
  R --> B["Book with the normal<br/>booking sheet (user confirms)"]

Key design decisions

  1. Show the interpretation. Users see what the AI understood, as chips they can edit or remove. This is the single most important trust pattern here.
  2. Results use existing components (ClassCard), so they're consistent and familiar.
  3. "Why this class": one short line per result ("Beginner-friendly · 8 min walk · Wed 18:30").
  4. The AI never books. Booking always goes through the normal sheet with the cancellation rule. AI suggests; the user acts.
  5. Label what it does, not that it's AI. "Find me a class" beats a ✨ sparkles button, an icon NN/G calls inherently ambiguous (source).

🧠 Concept 3: Designing for unpredictable output

The same request can give different results, and sometimes wrong ones. Design every state:

Situation Design
Clear request Chips + results
Vague request ("something fun") Ask one clarifying question with tappable options (e.g., "Calm / Energetic / Social")
Out of scope ("book me a massage at 3am at home") Say what it can do, offer the closest alternative
No results Show which chip is most limiting; one-tap "widen" ("Show classes up to 5 km")
Misinterpretation Chips make it obvious; one tap to fix
Slow response Show chips progressively; skeleton ClassCards
Service error Fall back to normal filters with what was typed
Sensitive input (injury, pregnancy, health) Don't give medical advice; suggest filtering "low-impact" and "check with the studio"

🧠 Concept 4: The AI behaviour spec (designers write this now)

Developers configure the model with instructions, but what the AI should and shouldn't do is a design decision. AI-native designers write a behaviour spec in plain language.

🧾 Real artifact: "Find me a class" behaviour spec (excerpt)

## Goal
Turn a user's wish into search criteria + a ranked shortlist of bookable classes.

## Always
- Output criteria as chips: activity types, days/times, distance, level, price.
- Prefer beginner-friendly classes when the user signals they're new.
- Explain each result in ≤ 8 words using real attributes (no invented claims).
- Use Movewell words: class, studio, book, credits.

## Never
- Never book, cancel or pay. Only suggest.
- Never invent classes, prices, instructors or availability.
- Never give medical advice; for health mentions, suggest low-impact filters and
  "check with the studio".
- Never use guilt or pressure ("You haven't worked out in a while!").

## When unsure
- Ask ONE clarifying question with 2–4 tappable options.

## Tone
Warm, brief, encouraging. No exclamation marks. No emoji.

🧠 Concept 5: Test sets: "unit tests" for AI behaviour

Because outputs vary, you test with a set of realistic inputs and check behaviour against the spec. These are often called evals. Designers increasingly own the user-facing part of them.

🧾 Real artifact: test set (excerpt)

# Input Expected behaviour Pass?
1 "yoga tomorrow morning" Chips: Yoga · tomorrow · before 12:00
2 "something relaxing after work this week" Calm activities, Tue–Fri after 17:30
3 "I'm new and nervous" Asks activity OR shows beginner-friendly options first; reassuring tone
4 "cheap spin near work" Asks for the work location if unknown; price chip
5 "classes for my bad knee" No medical advice; low-impact suggestion; "check with the studio"
6 "book me the 7pm one" Doesn't book; opens the booking sheet for the user to confirm
7 "asdfgh" Friendly "didn't get that" with example prompts

Run each input several times. Look for range, not just one good answer. Re-run the set when the model or instructions change.

🧠 Concept 6: Prototype it with a real model

Static frames can't show AI behaviour. Options with your tools:

  • Codex: a throwaway prototype (in a branch) connected to a real model, using the app's real components. The developers handle the API keys; never paste keys into prompts.
  • Figma Make: good for the UI flow with scripted or varied sample responses; check with developers if you need it connected to a live model.

Test with real users (Chapter 11), and log what the AI said in each session. Findings depend on it.

🧠 Concept 7: Trust, transparency and disclosure

  • Show sources and reasons: the "why this" line uses real attributes only.
  • Feedback: a light "Not what I wanted" control that removes or edits chips (better than a thumbs-down that goes nowhere).
  • Disclosure: NN/G's PACED framework helps decide how to disclose AI use: Policy, Audience, Context, Expectations, Degree. EU transparency obligations for some AI-generated content started applying in August 2026 (NN/G). Involve your legal team. For "Find me a class", a small note under the input ("Suggestions are generated from your request; check details before booking") is a reasonable start.
  • Human-AI guidelines worth knowing: Microsoft HAX Toolkit and Google PAIR Guidebook.

  • Behaviour spec template + test-set template: checklists.md

🧠 Concept 2: When PMs and developers generate UI

NN/G's view: in many organisations designers are no longer the only ones producing designs, and gatekeeping is counterproductive. The goal is to ensure everything AI generates, no matter who prompts it, is informed by the organisation's user knowledge and design standards (NN/G).

Situation ❌ Turf response ✅ AI-native response

Developer's agent fills undesigned states "Don't do that." "Let's design them together now (20 min), and I'll add them to the component so the agent finds them next time."

Give everyone the context

The most effective move: share your AI setup.

  • Make the Make kit the default for anyone prototyping.
  • Keep DESIGN.md and UX.md in the code, where developers' agents read them.

## Overview

Warm, energetic but calm. Feels like a friendly front desk, not a sales funnel. Clear information first: when, where, how hard, what it costs, what happens if you cancel.

## Colors

- **action-primary** is the only colour for primary actions, links and selected controls. Never decorative.

- All text/background pairs meet WCAG 2.2 AA (4.5:1 text; 3:1 large text and UI parts) in light and dark.

## Typography

- One family: Inter. Max 3 sizes per screen.

## Layout & spacing

- 4px base; use spacing tokens only. Related items: sm. Groups: md. Sections: lg.
- Primary actions in the thumb zone (bottom of screen / sheet).

## Shape & elevation

- rounded.md for cards and inputs, rounded.lg for sheets, rounded.full for chips and avatars.
- One shadow level for raised cards; none in dark mode (use surface-raised instead).

## Do

- Show the cancellation rule **before** the Book button.
- Show difficulty and "Beginner-friendly" when true.
- Use tokens for every value.

## Don't

- No gradients, glows or more than one shadow level.
- No emoji in UI text.
- No new colours outside this file.
- No ✨ sparkles to label AI features; label what the feature does.

UX.md: Movewell

Purpose: what every AI tool (and every person) should know about Movewell's users and how the product behaves. Inspired by NN/G's UX.md idea (UX-Context Design). Owner: Senior product designer · Last reviewed: [date] · Update after every research round and whenever AI output gets something wrong. Related: DESIGN.md (visual rules) · Glossary (below) · Components: app component library

1. Product in one paragraph

Movewell lets people discover and book local fitness and wellness classes (yoga, pilates, spin, climbing intros, sound baths) from partner studios. Users pay per class (euro) or with credits from a membership. Studios set prices, capacity and cancellation rules.

2. User models

Busy professional (primary) - 25–45, books 1–3 classes/week, often one-handed on the commute - Goal: book a good class in < 30 seconds - Frustrations: surprise fees, hidden rules, too many taps - Design implications: scannable facts first; primary actions in thumb zone; ≤ 3 taps to book

Beginner (secondary) - Trying a new activity; worried "is this too hard / will I fit in?" - Design implications: difficulty and "Beginner-friendly" visible; "what to expect / what to bring" on class details; reassuring tone

3. World model (context of use)

  • Often on the move, interrupted, with bad connectivity → preserve state; offline-friendly booking list; clear retry
  • Booking decisions often last-minute (same day) → availability and "spots left" prominent
  • Studios differ in rules → always show the studio's rule, never a generic one

4. Insights → constraints

# Insight (evidence, date) Constraint for anything we generate
1 Users feel tricked by late-cancel fees (14/18 interviews, Sep 2026) Show the cancellation rule BEFORE the Book button, with the fee amount
2 Beginners skip classes that look intense (9/12, Sep 2026) Show difficulty + "Beginner-friendly" when true; never hide level
3 Most bookings happen one-handed (analytics, 2026) Primary actions in thumb zone; ≤ 3 taps from class to booked
4 Users miss that recurring = weekly charges (4/5 tests, Oct 2026) Show "€X every [weekday]" next to any recurring control
5 Users expect a push notification when a studio cancels (5/5 tests, Oct 2026) Any studio-initiated change notifies the user and explains refunds

5. Interaction standards

  • Booking: booking sheet with summary (time, place, price, rule) → Book → success with "Add to calendar".
  • Cancel: free cancel = immediate with 10 s undo; fee cancel = confirmation dialog stating the fee.
  • Errors: what happened + what to do next. Never blame the user. No exclamation marks.
  • Loading: skeleton ClassCards; never block the whole screen for partial loads.
  • Empty states: explain the value + one action (e.g., "Find a class").
  • AI suggestions: AI suggests; the user confirms any booking, payment or cancellation.

Glossary

Agent. An AI that pursues a goal over several steps, using tools (read Figma, write code, run it) and checking its results. Examples: Codex, ChatGPT Work.

AGENTS.md. A file in the app's code with instructions for coding agents. Developers own the code rules; design co-owns the design-system rules.

Agent Skills / custom skills. Reusable instructions in a Markdown file that an agent loads when relevant. In Figma, you invoke them with a slash command (for example /movewell-ds-check).

Articulation barrier. The difficulty users have putting what they want into words for an AI. Hybrid UIs (prompt + controls) reduce it.

Behaviour spec. A plain-language description of what an AI feature must always do, never do, do when unsure, and its tone.

Branch. A safe copy of the code to work on without affecting the main version.

ChatGPT Project. A ChatGPT workspace with instructions and files that apply to every chat in it. It's your product's global context.

Code Connect. A Figma feature linking each Figma component to its real code component, so Dev Mode and the Figma MCP server show and use the real one.

Code to canvas. A Figma MCP capability that captures running UI from a browser into flat Figma layers (not linked to your library). Good for review.

Codex. OpenAI's coding agent, part of paid ChatGPT plans. It works in the ChatGPT desktop app, on the web, in the CLI and in editors.

Context. Everything an AI can see when it works: your message, files, project instructions, connected tools.

Context: global / local / ambient. Global = stable knowledge for all tasks. Local = specific to one task. Ambient = raw streams such as Slack or meeting notes (from NN/G).

Design token. A named design decision stored as data (color/action/primary = #0F7A6C). In Figma: a variable.

DESIGN.md. An open format (Google Labs, alpha) describing visual identity to AI tools: exact values plus plain-language rules.

Drift. Any difference between design intent and what was built.

DTCG. The W3C Design Tokens Community Group. It published the first stable token format specification (2025.10).

Evals / test set. A list of realistic inputs and expected behaviours used to check an AI feature, run several times.

Fidelity trap. Mistaking a polished prototype for production-ready work.

Figma agent. The AI agent inside Figma Design and Figma Make. It can use your connected library and @-mentions, and run custom skills.

Figma Make. Figma's AI prompt-to-app tool for interactive prototypes and apps.

Figma MCP server. Figma's MCP adapter. It lets AI agents read your designs, write to your canvas (beta) and capture live UI.

Hallucination. AI stating false information confidently.

Make kit. A Figma Make setup that imports your library's variables and styles, optional code packages and guidelines, so prototypes are on-system.

MCP (Model Context Protocol). An open standard for connecting AI tools to apps and data.

Mode. Alternative values for the same variables (for example Light/Dark).

Plugin (ChatGPT/Codex). Packaged skills and MCP connections installed from the Plugins directory (for example the Figma plugin).

Preview build. A version of the app you can try before release.

Primitive / semantic token. Primitive = the raw palette (teal/700). Semantic = meaning (color/action/primary). Components use semantic tokens.

Prop / property. Settings of a component: property in Figma, prop in code. Names should match.

Pull request (PR). A proposal to merge changes into the main code, with review.

Sycophancy. AI's tendency to agree with and flatter you.

Synthetic users. AI-generated stand-ins for research participants. Use them for rehearsal, not evidence.

Twins. Matching items in Figma and code: variable↔token, component↔component, property↔prop, mode↔theme.

UX.md. A context file with users, research insights written as constraints, interaction standards and the glossary (NN/G's idea).

UX-context design. Curating what the organisation knows about users and standards into context that guides every AI tool (NN/G).

Write to canvas. A Figma MCP capability (beta) where agents create and edit real Figma content using your components and variables.
